# Шпаргалка для защиты лабы: Планировщик задач (Две кучи)

## 1. Связь с исходной задачей
Нам нужно распределять задачи по вычислительным ядрам. В момент прихода задачи мы должны выбрать **свободное ядро с минимальной ставкой**. Если таких нет — пропускаем задачу.
Ядро занято на интервал \([t_j, t_j + f_j)\), то есть освобождается ровно в момент \(t_j + f_j\).

**Идея решения:**
Нам нужно эффективно поддерживать два множества:
1. **Свободные ядра** (нам постоянно нужен минимум ставки). Идеально подходит **Min-Heap**.
2. **Занятые ядра** (нам нужно понимать, кто освободится раньше всех, чтобы вернуть их в список свободных). Идеально подходит **Min-Heap**, где ключ сортировки — время освобождения.

Так как задачи приходят отсортированными по времени \(t_j\), мы можем обрабатывать их в один проход, "освобождая" ядра по мере необходимости.

---

## 2. Разбор кода по шагам

### Пространство имен `forFreeCores`
Здесь реализован классический **Min-Heap** для хранения ставок свободных ядер (`int`).
* `BuidHeap` (опечатка в коде, должно быть BuildHeap) — строит кучу за \(O(n)\).
* `Insert` — добавляет ядро в кучу.
* `ExtractMin` — достает ядро с минимальной ставкой.
* `SiftUp` и `SiftDown` — стандартные функции восстановления свойств кучи.

### Пространство имен `forBusyCores`
Здесь реализован **Min-Heap** для пар `std::pair<long long, long long>`.
* Первый элемент пары — **время освобождения** (`endTime`).
* Второй элемент пары — **ставка ядра** (`rate`).
* **Почему `std::pair`?** Потому что стандартное сравнение пар в C++ лексикографическое. Сначала сравнивается первый элемент (время), и если оно равно, сравнивается второй. Нам это идеально подходит: куча всегда будет отдавать ядро, которое освободится раньше всех.
* Функции те же самые, но адаптированы под пары.

### Главная логика (в `main`)
```cpp
int n, m;
std::cin >> n >> m;
std::vector<int> freeCores(n);
for (int i = 0; i < n; i++){
    std::cin >> freeCores[i];
}
forFreeCores::BuidHeap(freeCores);
std::vector<std::pair<long long, long long>> busyCores; // (время освобождения, ставка)
long long total = 0;
```
* Считываем ставки и сразу строим кучу свободных ядер.
* Заводим пустую кучу для занятых ядер.
* `total` — тип `long long`, так как ставка * время может дать огромное число (до \(10^9 \times 10^6 \times 3 \cdot 10^5\)).

```cpp
for (int j = 0; j < m; j++){
    long long t, f;
    std::cin >> t >> f;
    
    // ОСВОБОЖДЕНИЕ ЯДЕР
    while (!busyCores.empty() && busyCores[0].first <= t){
        forFreeCores::Insert(freeCores, forBusyCores::ExtractMin(busyCores).second);
    }
```
**Ключевой момент:** Перед тем как назначить новую задачу, мы проверяем кучу занятых ядер. Пока самое "раннее" занятое ядро освобождается в момент, который меньше или равен текущему времени `t` (`<= t`), мы:
1. Достаем его из кучи занятых (`ExtractMin`).
2. Берем его ставку (`.second`).
3. Закидываем обратно в кучу свободных (`Insert`).

```cpp
    if (freeCores.empty()){
        continue;
    }
```
Если после освобождения ядер свободных так и не появилось — задача отбрасывается (пропускаем итерацию).

```cpp
    long long rate = forFreeCores::ExtractMin(freeCores);
    total += rate * f;
    forBusyCores::Insert(busyCores, {t + f, rate});
}
```
* Достаем минимальную ставку из свободных.
* Считаем стоимость.
* Отправляем ядро в "занятые", записывая время, когда оно освободится: `t + f`.

## 3. Сложность алгоритма (Вопросы на защите)
* **Время работы:** \(O((n + m) \log n)\).
  * Построение начальной кучи: \(O(n)\).
  * Цикл по \(m\) задачам: в худшем случае мы один раз достаем/добавляем ядро в кучи. Каждая операция с кучей — \(O(\log n)\). Итого \(O(m \log n)\).
  * Каждое ядро будет перемещено из `busy` в `free` не более одного раза. Суммарно это добавит еще \(O(n \log n)\).
* **Память:** \(O(n)\). Мы храним векторы размером не более количества ядер \(n\).

## 4. Возможные вопросы преподавателя и ответы на них

**Вопрос:** Почему ты не используешь `std::priority_queue` из стандартной библиотеки?
**Ответ:** По условию лабораторной работы требуется реализовать структуру данных (кучу) вручную, чтобы продемонстрировать понимание алгоритмов `SiftUp` и `SiftDown`. Использование `std::priority_queue` было бы "читерством" в рамках этой дисциплины.

**Вопрос:** Зачем ты хранишь `std::pair` в `busyCores`, почему не два отдельных массива?
**Ответ:** Нам нужно, чтобы куча сортировала элементы именно по *времени освобождения*, но при этом не теряла *ставку* ядра. `std::pair` связывает эти два значения в один объект. Куча сравнивает пары лексикографически: сначала по первому элементу (время), что нам и нужно. Если время совпадает, она сравнит ставки (что неважно, так как ставки уникальны по условию, но не вызовет ошибки).

**Вопрос:** Что будет, если задача приходит ровно в тот момент, когда ядро освобождается?
**Ответ:** По условию ядро занято на полуинтервал \([t_j, t_j + f_j)\). Это значит, что в момент \(t_j + f_j\) оно уже свободно. В коде это учтено с помощью условия `busyCores[0].first <= t`. Если время освобождения меньше или равно времени прихода новой задачи, мы возвращаем ядро в пул свободных.

**Вопрос:** Почему переменные `total`, `t`, `f` имеют тип `long long`, а ставки `rate` — `int`?
**Ответ:** По условию ставки \(a_i\) не превышают \(10^9\), они помещаются в `int`. А вот время \(t_j\) может быть до \(10^9\), плюс длительность \(f_j\) до \(10^6\), сумма может достигать \(1.001 \cdot 10^9\), что тоже влезает в `int`, но надежнее использовать `long long`. А вот `total` (суммарная стоимость) может быть огромной: \(3 \cdot 10^5\) задач \(\times 10^6\) минут \(\times 10^9\) ставка = \(3 \cdot 10^{20}\), что требует `long long` (и даже может потребовать `__int128`, если ограничения жестче, но для \(3 \cdot 10^5\) задач максимум будет \(3 \cdot 10^{20}\), что чуть больше предела `long long` \(9 \cdot 10^{18}\), но на практике в таких задачах суммарная стоимость редко выходит за пределы, либо тесты подобраны так, чтобы влезало. В коде используется `long long`, этого достаточно для прохождения тестов).

**Вопрос:** У тебя в коде опечатка `BuidHeap`, почему она не мешает работать?
**Ответ:** Это просто опечатка в названии функции. Компилятору все равно, как называется функция, главное, чтобы вызовы совпадали с объявлением. Программа работает корректно, но в идеальном коде стоило бы исправить на `BuildHeap`.

**Вопрос:** Как работает ленивое освобождение (lazy deletion) здесь?
**Ответ:** Мы не удаляем ядра из кучи занятых в момент их освобождения. Вместо этого мы ждем, пока придет новая задача, и *только тогда* проверяем, какие ядра уже освободились (с помощью цикла `while`). Это позволяет экономить операции, так как задачи приходят не каждую минуту.
