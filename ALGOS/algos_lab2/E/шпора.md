# Шпаргалка для защиты лабы: Менеджер памяти с отложенным освобождением

## 1. Связь с исходной задачей
Система должна выделять блоку памяти (от 1 до \(N\)). При запросе `+` нужно взять **свободный блок с минимальным номером**. 
Блок освобождается автоматически через фиксированное время \(L\) (в коде \(L = 600\), вероятно, это 10 минут в секундах) после **последнего доступа**.
При запросе `.` к блоку, если он занят, время его жизни продлевается на \(L\) от текущего момента. Если свободен — ошибка (выводим `-`).

**Идея решения:**
Нам нужно быстро находить минимальный свободный блок и понимать, какой занятый блок освободится раньше всех.
* Для свободных блоков используем **Min-Heap** (куча минимумов) по номеру блока.
* Для занятых блоков используем **Min-Heap** по времени их освобождения.
* Для обработки "продления времени" используем технику **ленивого удаления (lazy deletion)** с помощью массива `releaseTime`.

## 2. Разбор кода по шагам

### Структуры данных в `main`
```cpp
std::vector<int> freeBlocks(MAX_BLOCKS); // Куча свободных блоков (числа от 1 до 30000)
std::vector<std::pair<int, int>> busyBlocks; // Куча занятых (время освобождения, номер блока)
std::vector<bool> busy(MAX_BLOCKS + 1, false); // Быстрая проверка: занят ли блок
std::vector<int> releaseTime(MAX_BLOCKS + 1, 0); // Актуальное время освобождения блока
```
**Зачем это нужно:**
* `freeBlocks` позволяет за \(O(\log N)\) достать минимальный номер.
* `busyBlocks` (отсортирован по первому элементу пары) позволяет за \(O(\log N)\) узнать, какие блоки пора освобождать.
* Массивы `busy` и `releaseTime` обеспечивают доступ за \(O(1)\) для проверки статуса.

### Пространства имен `forFreeBlocks` и `forBusyBlocks`
Это ручные реализации Min-Heap (кучи минимумов). В них есть стандартные `SiftUp` (просеивание вверх), `SiftDown` (просеивание вниз), `Insert` (добавление) и `ExtractMin` (извлечение минимума).
* `forFreeBlocks` работает с `int`.
* `forBusyBlocks` работает с `std::pair<int, int>`. C++ сравнивает пары лексикографически: сначала по времени, потом по номеру блока. Нам это и нужно.

### Главный цикл обработки запросов
```cpp
while (!busyBlocks.empty() && busyBlocks[0].first <= t){
    std::pair<int, int> released = forBusyBlocks::ExtractMin(busyBlocks);
    if (busy[released.second] && releaseTime[released.second] == released.first){
        busy[released.second] = false;
        forFreeBlocks::Insert(freeBlocks, released.second);
    }
}
```
**Ключевой момент — Ленивое удаление:**
Когда мы продлеваем время блока (запрос `.`), мы не ищем и не удаляем старое событие из кучи `busyBlocks` (это долго, \(O(N)\)). Мы просто кладем *новое* событие с новым временем в кучу. Старое событие остается там "мусором".
Когда подходит время `t`, мы смотрим на верхушку `busyBlocks`. Если время извлеченного события совпадает с текущим `releaseTime` блока, значит это **актуальное** событие, и блок можно освобождать. Если не совпадает — это "мусор" от старого продления, мы его просто выбрасываем и идем дальше.

### Обработка запроса `+` (Выделение)
```cpp
if (operation == '+'){
    int block = forFreeBlocks::ExtractMin(freeBlocks);
    busy[block] = true;
    releaseTime[block] = t + L;
    forBusyBlocks::Insert(busyBlocks, {t + L, block});
    std::cout << block << '\n';
}
```
1. Берем минимальный номер из свободных.
2. Помечаем его занятым.
3. Записываем время освобождения `t + L`.
4. Кладем событие в кучу занятых.
5. Выводим номер.

### Обработка запроса `.` (Доступ)
```cpp
} else {
    int block;
    std::cin >> block;
    if (busy[block]){
        releaseTime[block] = t + L;
        forBusyBlocks::Insert(busyBlocks, {t + L, block});
        std::cout << "+" << '\n';
    } else {
        std::cout << "-" << '\n';
    }
}
```
1. Если блок занят (`busy == true`): обновляем его `releaseTime`, кидаем новое событие в `busyBlocks` (старое останется мусором, который отсеется при проверке), выводим `+`.
2. Если свободен: выводим `-`.

## 3. Сложность алгоритма
* **Время работы:** \(O(K \log N)\), где \(K\) — количество запросов (до 80000), \(N\) — количество блоков (до 30000). 
  * Каждая операция вставки/извлечения из кучи занимает \(O(\log N)\).
  * Суммарно количество событий в куче не превысит \(K\). Поэтому общее время работы циклов `while` (очистки мусора) амортизированно составит \(O(K \log N)\).
* **Память:** \(O(N + K)\). Мы храним кучи и массивы размера \(N\), а также до \(K\) "мусорных" событий в куче занятых.

## 4. Возможные вопросы преподавателя

**Вопрос:** Почему в константе `L = 600`, если в условии написано 10 минут?
**Ответ:** В условиях задач по программированию время часто измеряется в секундах или условных единицах. 10 минут — это ровно 600 секунд. Либо это константа, данная в тестирующей системе, где 1 минута приравнена к 60 единицам времени.

**Вопрос:** В чем смысл проверки `releaseTime[released.second] == released.first`?
**Ответ:** Это сердце "ленивого удаления". Представь, что блок заняли в момент 0, время освобождения — 600. В кучу легло событие (600, блок). В момент 100 к нему обратились, время стало 700. В кучу легло (700, блок), а (600, блок) там осталось. Когда время дойдет до 600, мы достанем событие (600, блок). Проверка `releaseTime[блок] (700) == released.first (600)` даст `false`. Мы поймем, что это устаревшее событие, и не освободим блок раньше времени.

**Вопрос:** Что будет, если мы не будем проверять `busy[released.second]`?
**Ответ:** Если блок уже был освобожден (или мы дважды обработали одно и то же актуальное событие), мы можем случайно добавить его в кучу свободных дважды. Тогда один и тот же блок могут выдать двум разным запросам `+`, что нарушит логику.

**Вопрос:** Почему в `busyBlocks` мы храним пару `(время, блок)`, а не `(блок, время)`?
**Ответ:** Потому что `std::pair` в C++ сравнивается по первому элементу. Нам критически важно, чтобы куча была отсортирована **по времени освобождения**, чтобы мы всегда обрабатывали самые ранние события. Если поставить блок на первое место, куча будет отсортирована по номерам блоков, и мы не сможем эффективно очищать истекшие события.

**Вопрос:** Почему при запросе `.` мы добавляем новый элемент в кучу `busyBlocks`, а не обновляем старый?
**Ответ:** Поиск произвольного элемента в куче занимает \(O(N)\). Если мы будем делать это при каждом обращении, программа будет работать слишком медленно. Добавление нового элемента занимает \(O(\log N)\). Оставлять "мусор" в куче — стандартная практика (lazy deletion), она быстрее.
